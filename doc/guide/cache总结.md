常见的缓存模式
项目代码中一般有两种缓存模式：本地缓存和Redis缓存。Redis使用内存做为缓存，内存的结构决定了访问速度快、容量小，所以Redis缓存常被用于保存热点数据Hotpot。
1、本地缓存管理器
策略：
（1）缓存刷新：从数据库获取数据时同步更新本地缓存，更新本地缓存这一操作利用 CAS 机制或分段锁技术处理并发更新，保证每次更新数据都是单线程（防止并发更新的问题）
（2）本地缓存过期清理：设置缓存过期时间，内部采用LRU的方式自动淘汰（双向循环链表）
（3）缓存查找：hash访问缓存，如果缓存没命中则访问数据库，同步更新最新数据到缓存中
2、使用Redis做本地缓存
如何访问？先访问缓存再访问数据库，如果缓存没命中则访问数据库，同步更新最新数据到缓存中。-- 旁路模式
涉及到缓存的设计模式为Cache-Aside Pattern，有5个关键点：
- 收到应用的请求时，首先去cache中检查该数据是否在缓存中
- 缓存命中，直接返回缓存中的数据，确保数据快速使用
- 缓存Miss，应用从主数据库中检索数据
- 缓存填充 Cache Population，从数据库中获取的数据将其副本保存至缓存中，以便下一次请求过来可以直接使用
- 数据使用，将获取到的数据交由应用程序使用
  优点：该模式降低了数据库的负载、加速数据访问、广泛用于提高应用访问的效率及可扩展性。
  旁路模式的设计原则：
- Lazy Loading延迟加载：数据仅在使用时加载到缓存，cache miss时从主数据库中获取再存到缓存中
- 缓存作为独立的组件：缓存对味一个独立层，和主数据库分离。应用同时和数据库、缓存交互，决定什么时候读写缓存
- 直读/直写：对于读操作，应用会先访问缓存，缓存中数据找不到从数据库中获取数据，把该数据存在缓存中；对于写操作，应用直接更新数据库，根据需要处理缓存失效或者缓存更新，以保证数据一致性。
- 缓存淘汰策略（Cache Eviction Policy）：由于缓存存储容量的限制，合理的淘汰策略（LRU）用于移除最不常用最久的数据，给新数据腾出空间，确保了缓存有效和关联性
- 数据一致性和过期：策略必须维护数据库和缓存数据的一致性，包括设置过期时间以使得缓存刷新数据或者在数据库修改时使用缓存失效技术
- 性能优化：首要的目标是减少数据库延迟（latency）和负载（load），通过从缓存中提供频繁访问的数据，系统能够响应更快、处理更多请求
- 可扩展：该模式通过在缓存和数据库之间分别读取数据帮助系统可扩展，使得系统能够在不成比例（proportional）增加数据库负载的情况下拦截更多的流量（Trafic）

  缓存填充策略
  1、旁路模式（延迟加载）：是指仅在应用程序请求数据时才将其加载到缓存中。应用程序首先检查缓存中是否存在所需数据，如果未找到（缓存未命中），则从数据库中检索数据，将其存储到缓存中，然后再返回给应用程序。这种方法仅存储实际需要的数据，从而确保了缓存空间的高效利用，但可能会导致首次访问延迟。（Cache-Aside (旁路)：应用程序代码 负责逻辑（App 查缓存 -> Miss -> App 查库 -> App 写缓存））
  2、直读：该策略将数据加载的责任转移到缓存本身，当应用请求数据时，缓存先检查是否存在，数据不存在那么缓存从数据库中获取数据存起来，再将数据返回给应用。因为缓存自行管理数据，它简化了应用管理的逻辑，确保模式一致的访问，但是仍然存在首次访问数据延迟的问题。（Read-Through (直读)：缓存组件本身 负责逻辑（App 向缓存要数据 -> 缓存内部 Miss -> 缓存组件自己去查库并回填 -> 返回给 App），App 感知不到数据库的存在）
  3、直写：每次写操作都同时更新缓存和数据库，当应用写数据时，它确保缓存和数据库保持同步通过在同时写入缓存和数据库。这一策略保证了缓存总是最近的数据，降低了缓存失效的情况。然而由于需要双写，写操作会很慢，它增加了维护数据库和缓存一致性数据的复杂性。
  4、回写：写操作会先写缓存再异步传递至数据库，这种方法可以降低应用程序感知到的延迟，从而提高写入性能，因为数据在缓存中可以立即使用。然而，它引入了确保数据一致性的复杂性，当数据库更新和缓存更新存在时差时，在缓存写完成后缓存故障会潜在地导致数据丢失和脏数据。
  缓存失效的挑战和解决方法
  缓存失效的挑战：
- 数据丢失：如果数据库数据更新而缓存数据没更新导致缓存返回给应用的数据是过期的。用户收到错误或者过时的数据，用户体验和业务决策失误
- 并发问题：当存在多个数据更新的请求时，存在在数据库和缓存之间的静态条件，导致某些更新无法正确的显示在缓存中。导致数据库和缓存数据不一致
- CacheMiss惩罚：缓存失效后需要下一个请求执行数据库查询。增加了后续请求的延迟
  缓存失效的解决方法：
- 显式失效：当数据库中的数据有修改时，需要显示更新缓存中的数据。优点：提供更准确、更及时的缓存与数据库一致性。缺点：增加应用程序逻辑的复杂性，需要仔细协调数据库和缓存的更新。
- 直写/回写的策略：不管缓存数据有更新还是数据库中的数据有更新，都立刻更新数据库和缓存。优点：确保缓存始终包含最新数据，降低提供过时信息的可能性。缺点：由于同步更新，直写式可能速度较慢；而如果管理不当，后写式可能导致暂时性不一致。（直写和回写的视角都是数据库，直写直接写入缓存和数据库，回写先写缓存再回写数据库）
- 缓存版本：每个缓存对象都维护个版本号，当缓存数据更新时，缓存版本号+1。优点：有助于跟踪数据变更，确保仅提供最新版本的数据。缺点：增加管理版本号的开销，并可能使缓存检索逻辑复杂化。
- 事件驱动的缓存失效：当应用监听到数据库中的数据有变化，触发缓存失效，使用事件驱动的方式更新缓存。优点：提供实时缓存更新和失效，确保高度一致性。缺点：需要强大的事件管理系统，并可能增加事件传播和处理的复杂性。
- 缓存预热：在应用程序启动期间或缓存失效后，使用频繁访问的数据预加载缓存，优点：通过确保常用数据已存在于缓存中，降低缓存未命中惩罚。缺点：可能会增加启动时间和数据库的初始负载。
  在旁路模式下处理CacheMiss，Error，超时TimeOut
  处理CacheMiss
- 高效数据恢复：发生CacheMiss时，示更新缓存中的数据
- 批处理：当出现多个CacheMiss时，以批处理的方式降低数据库负载
- 缓存预热：在应用启动或者在某个非活动状态之后用热点数据预回填缓存
  处理Error -- 问题明确，确定性失败
- 优雅降级：在缓存或者数据库暂时不可用时，简化业务处理的流程。确保应用依然能合理的使用
- 重试机制：当连接缓存或者数据库连接异常时，实现重试逻辑
- 监控和告警：持续监控缓存和数据库的健康状态，并设置异常警报
  处理超时 -- 问题不确定，不确定状态
- 超时配置：配置合适的超时时间以避免长时间等待
- 回退策略：当缓存或数据库操作超时时，实施回退机制
- 熔断模式：使用熔断器避免系统级联故障（cascading failures），防止拖垮整个链路（雪崩效应）
  增强旁路模式性能的优化技术
- 高效的数据管理：（1）使用合适的过期策略：对缓存数据设置TTL最大存活时间以确保数据定期更新。每次连接时逐步延长TTL，以确保缓存数据长时间存活（2）缓存淘汰策略：LRU/LFU/FIFO的过期策略去管理缓存容量，确保相关数据保存在缓存中
- 预加载和预热策略：（1）缓存预加载：在应用启动时预加载热点数据，降低首次CacheMiss。通过分析使用模式识别热点数据，并确保提前将其缓存（2）后台缓存预热：使用定时任务定期更新和预加载缓存中的数据，在服务流量低谷时回填缓存中的数据，在峰值时能够降低CacheMiss惩罚
  优化缓存访问模式
- 批处理：当CacheMiss发生时针对多个访问数据库的请求使用批处理的方式访问，降低轮训数据库的数量
- 多级缓存策略：使用多级缓存策略（本地缓存-内存、分布式缓存）平衡速度和容量
  一致性和失效策略
- 高效的缓存失效机制：实施细粒度的失效策略，仅更新或者移除受到影响的缓存数据而不是大面积的更新所有缓存数据，只有当必要的时候，使用版本控制或者时间戳去校验缓存数据的失效
- 事件驱动更新：使用事件驱动架构将数据库的修改及时同步到缓存中，确保缓存数据总是最新的。使用消息队列或者发布订阅系统（例如 Kafka、RabbitMQ）处理失效事件，即：当 DB 变更，发送消息到 Redis Channel，所有应用节点监听该 Channel 并删除本地/分布式缓存。
  扩展缓存架构
  1、水平扩展：将缓存数据分布到多个缓存节点上。实现：使用一致性哈希或预定义的分片键将数据均匀分布到各个节点上。一致性哈希可以最大限度地减少在添加或删除节点时需要重新分发的数据量。优势：分散负载、提高容量并增强容错能力，确保即使一个节点发生故障，其他节点仍然可以正常运行。示例：在 Redis 中，Redis 集群会自动将数据分片到多个实例上，从而提供可扩展的解决方案。
  2、垂直扩展；增加现有缓存服务器的资源（CPU、内存）。实现：升级硬件或迁移到更大的虚拟机。
  优势：提高单个缓存节点的容量和性能。缺点：存在物理和成本限制；最终可能需要进行水平扩展。
  3、分布式缓存：使用原生支持分布式缓存的分布式缓存系统，例如 Redis 集群、Memcached 或 Apache Ignite。实现：搭建一个缓存节点集群，这些节点协同工作以存储和管理缓存。优势：提供可扩展性、高可用性和容错性。示例：Redis 集群将数据分区到多个 Redis 节点，并提供自动故障转移和复制功能。
  4、复制：描述：将缓存数据从主节点复制到一个或多个从节点。实现：配置缓存系统以将写入操作从主节点复制到从节点。优势：提高读取性能并提供数据冗余。缺点：写入操作仍然受限于主节点；可能会出现最终一致性问题。
  5、多级缓存：实现多层缓存，例如内存缓存（L1）和分布式缓存（L2）。实现方式：一级缓存（L1）使用内存缓存（例如 Ehcache 或 Guava），二级缓存（L2）使用分布式缓存（例如 Redis 或 Memcached）。优势：兼顾速度和容量，降低分布式缓存的负载。示例：将访问频率最高的数据存储在应用服务器的内存缓存中，将访问频率较低的数据存储在 Redis 中。如果 L2 (Redis) 更新了，如何通知成千上万个节点的 L1 (本地 JVM 缓存) 失效？---需要配合 Redis Pub/Sub 或 配置中心推送 来广播失效消息，否则 L1 会长期持有脏数据。
  实际案例
  缓存旁路模式（Cache-Aside pattern）广泛应用于各种高性能应用程序中，以优化数据检索并降低主数据存储的负载。以下是一些缓存旁路模式成功应用的实际案例：
  1、Netflix
  Netflix 使用缓存旁路模式来管理其庞大的电影和电视节目库，确保快速访问元数据和内容推荐。Netflix 使用基于 Memcached 构建的自定义实现 EVCache 来缓存常用数据。
  当用户请求内容元数据时，Netflix 首先检查缓存。如果数据不存在（缓存未命中），它会从后端数据库检索信息，将其缓存，然后提供给用户。
  这种方法显著降低了后端数据库的负载，确保了用户的低延迟，并提高了系统的可扩展性。
  2、Amazon
  Amazon 利用缓存旁路模式来优化其电子商务平台上的产品详情检索和库存数据管理。亚马逊结合使用 Redis 和 DynamoDB Accelerator (DAX) 等内存缓存解决方案来缓存产品详情和库存数据。
  对于每个产品详情请求，亚马逊首先会检查缓存。如果缓存中缺少数据，它会从主数据库获取数据，更新缓存，然后将结果返回给用户。
  这减轻了亚马逊主数据库的负载，确保在购物高峰期提供更快的响应速度和更好的用户体验。
  3、Facebook
  Facebook 使用 Cache-Aside 模式来管理用户会话数据和经常访问的社交图谱数据，例如用户个人资料和好友列表。Facebook 结合使用 Memcached 和 TAO（一种地理分布式数据存储）来缓存会话数据和社交图谱信息。
  当用户访问其个人资料或好友列表时，Facebook 首先会检查缓存。如果找不到数据，它会从主存储中检索数据，更新缓存，然后处理请求。
  这种方法帮助 Facebook 每天处理数十亿个用户请求，提供快速的数据访问并减轻主数据库的负载。
  如何对热点数据每次从数据库中获取数据后，同步刷新缓存？
  1、互斥锁 (Mutex Lock)：查库前，先在 Redis 设一个互斥锁 (setnx)。只有拿到锁的线程去查库并回写，其他线程等待或重试。
  2、逻辑过期：数据不设物理 TTL，而是在 Value 里存一个 expire_time 字段。读取时发现逻辑过期，异步启动一个线程去更新缓存，当前请求直接返回旧数据（保证可用性）。
